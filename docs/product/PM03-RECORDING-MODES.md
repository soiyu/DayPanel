# PM03 按量、按次与完成方式审查

2026-11-08，基线 `aba6234`（应用代码仍为215f026）。负责人纠正审查不能围绕喝水单项，需覆盖按量和按次完成。本报告将PM02的数量议题扩展为所有事项的记录模型、操作和考核规则；仍为审查与后续设计要求，未实现新记录类型、周累计或逐次事件。

## 先分清三个维度

1. **记录什么**：是否做过、累计数量、累计次数、是否需要每一次的独立明细。
2. **怎样算达标**：做过一次；当天量/次数达到目标；一周有N个达标日；一周累计N次或N单位。后三种周目标不能互换。
3. **什么时候需要做**：每天、指定日、间隔、周内自选、只做一次、按需使用。一次性/常驻小事是已有独立对象，不能偷偷变成重复习惯。

事项名称和图标只能提供起点，不能决定业务规则。同样的“阅读”可以是读过就完成、读20页或分两次读；同样的“整理”可以是每天一次、当天多次、一次性或按需。界面需要帮助用户表达用途，不要求用户先理解内部模型。

## 当前能力与缺口

| 真实用户用途 | 当前实现 | 需要的交互/规则 |
|---|---|---|
| 做过就完成：早餐、整理、一次练习 | 已有check；每习惯每天一个完成状态 | 明确完成/撤销，无数量输入；重复完成请求保持完成，不累计第二次 |
| 当天累计数量：阅读页数、跑步公里、练琴分钟、步数 | 已有quantity；每天一个数值，保存替换日总量 | 输入与单位/精度匹配，已有总量与保存结果清楚，取消不写；小数距离与整数计数不能统一限制 |
| 当天累计N次：练习3次、整理2次 | 可用quantity+“次”填写总次数；没有专用整数计数约束 | 需要明确的计数方式、整数目标与输入、合理快捷值、0/3和1/3进度；不能只换单位文字就称完整计次 |
| 一次一次记录，并撤销其中一次 | 没有独立事件；同一天多次保存仍只剩一个合计值 | 若纳入实施，须定义每次值、合计、重复提交、并发、编辑/撤销及历史；不能把盲加按钮当完整方案 |
| 每周至少N天达到当天标准 | 已有weekly，UI准确叫“每周达标天数”1–7 | 完整预览如“每周选3天，每个达标日练琴至少15分钟”；同一天做3次仍只算1个达标日 |
| 每周累计N次或累计数量 | 当前没有这两种目标模型 | 与周达标日数分开评估；不能静默把旧weekly解释为事件次数/总公里数 |
| 一次性待办 | 已有小事，完成后保留实际完成日，可重开 | 无每天重置，不为追求完成率要求用户每天重复 |
| 按需常驻 | 已有常驻小事，每天最多记录一次，不做不欠账 | 明确“今天做过”；不能代替同日多次计数或自动周期任务 |

## 已验证的跨事项问题

- **次数快捷值不合适**：目标3、单位“次”或“times”，`quantitySuggestions`实际给出0.75、1.5、2.25、3。代码在`habit_templates.dart:206`，通用未知单位按四分之一/一半/四分之三生成。诊断A已复现。
- **单位文字不能提供计数规则**：“次”作为quantity单位时，1.5能正常落库。诊断B已复现。需要新增明确的计数语义，不能依赖中文/英文单位猜测，也不能回头强制取整已有历史。
- **3次和3天不等价**：同一天依次保存总数1、2、3后，数据库只有当天总数3；若计划是每周达标3天，当前进度为1/3天。诊断C已复现。这符合旧规则，本身不是计算错误；创建流程必须让用户选对要求。
- **多提醒不代表多次任务**：同一个习惯的早晚提醒都指向同一个当天目标。check早上完成后，当天后续提醒取消；quantity总次数未达标时可继续提醒，达到目标后取消。没有“早晨一次/晚上一次分别勾选”的子项模型。见`ReminderRules.kt:25`。提醒编辑应明确此关系，不能擅自把提醒时刻改为任务配额。
- **创建选项缺少用途解释**：当前“完成打卡/数量目标”两个名称与一个水滴图标覆盖所有量化事项。应通过完成标准与实例解释类型，使用通用数量标识；模板不应让练琴/跑步等也被理解成饮水专用界面。

## 各类入口应怎样适配

| 路径 | 完成一次 | 按量 | 按次数 |
|---|---|---|---|
| 新建/模板 | 做过即完成，安排单独确认 | 数量、单位、目标与精度 | 整数目标、次数含义；区分日次数与周达标天数 |
| 日常主操作 | 明确完成/撤销 | 直接输入；本次量与改总量需明确区分 | 明确记录本次或修改总次数，显示提交后值，保存才写 |
| 详情 | 日期、是否做过 | 日期、实际量、目标、单位 | 日期、实际次数、目标；仅有日总数时不显示虚假逐次明细 |
| 历史/纠正 | 保留所选日期和原规则 | 按历史单位/目标，替换需明确 | 修正次数与撤销某次是不同动作；不能假设旧日总数有逐次来源 |
| 统计 | 按安排的达标日/连续性 | 分单位累计、趋势、适用完成率 | 次数、达标日数分开；同日3次不冒充3个连续日 |
| 提醒 | 达成当日目标即停止 | 未达目标继续，达标取消 | 按明确计次目标决定，不把N个提醒解释成N个已排程子任务 |
| 桌面 | 显式目标、防重复/旧动作 | 直达输入，确认才写 | 安全明确的目标值或经设计的事件；不依靠静态extras充当点击ID |
| 卡片 | 沿用当天规则 | 按历史目标达标 | 先明确是否属于日义务；周目标不偷偷纳入每日必须，历史补记不发卡 |

界面中状态、实际值、目标、日期应先于管理选项。没有逐次模型时不提供假的次数历史；没有周期累计目标时不显示假的周进度。保留PM02已列的创建落点、空态、计划外记录与搜索/回顾路径修复。

## 后续实施边界与验收调整

1. PM02A基础路径修复必须跨完成一次、页数、距离、分钟、次数总量、一次性和常驻验证，不能只用喝水做成功案例。
2. 先确定“完成一次/累计量/整数计次”的创建说明、校验、快捷值和完整规则预览。现有合法小数数量继续有效；旧quantity单位“次”不得静默迁为整数或抹去历史。
3. 本次量/独立次数事件、周次数/周累计量有不同的数据和考核含义，先记录明确ADR再实施；不为减少点击破坏确认、重复投递防护或撤销。既有目标/单位/频率修改次日生效，旧日期按旧版本。
4. 若新增字段/表，迁移、严格备份校验、导出/恢复/恢复前副本、旧版本兼容、提醒读取器、组件冷进程和App规则同步设计。恢复旧页generation、revision/ABA和事务保护继续保留。设备绑定不作为可恢复业务实例。
5. 新增验收至少覆盖：完成请求重复不翻转；阅读总量修改/取消；跑步2.5公里；分钟手动输入；3次目标无分数快捷值；按次重复投递/旧动作/撤销；同日3次与周3天的区别；两个提醒对应一个目标；一次性不重复、常驻每天最多一次；历史/恢复/桌面与统计一致。新能力未实现前不记作通过。
